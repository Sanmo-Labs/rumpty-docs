<Endpoint method={"POST"} path={"/v1/deployments/{uid}/custom-domains/{domain_uid}/verify"} />

Checks the domain's DNS records against its authoritative nameserver and, if they match,
queues a `verify_custom_domain` operation that issues a TLS certificate and routes the
domain to the deployment. The domain stays `pending` until that operation finishes and
becomes `active`.

As soon as the checks pass, the deployment's `custom_domain` and `public_url` switch to
this domain. Environment variables that were seeded from the public URL (as one-click apps
do) are rewritten to the new domain and re-applied if the app is live.

If a DNS check fails, the domain is marked `failed` with the reason in `last_error`, and
the request returns `400` with the same message. The app must have been deployed first.

Calling this again is safe:

- If the domain is already `active`, you get `status: succeeded` with an empty
  `operation_id` and nothing is queued.
- If a verification queued in the last 15 minutes is still running, that operation is
  returned instead of a new one.

Otherwise this is asynchronous and returns `202 Accepted` with an `operation_id`. See
[Get an operation](/api/operations/get-an-operation).

## Errors

| Status | Meaning |
|---|---|
| `400` | DNS verification failed, the domain is a root domain, or the app is not deployed yet (`deploy the app before verifying a custom domain`, `deployment does not have a default hostname yet`). Example DNS messages: `CNAME record has not propagated or does not point to <hostname>`, `verification TXT record not found or does not match: <verification_txt>`. |
| `401` | The API key is missing, invalid, expired or revoked. |
| `403` | You cannot access the workspace, your role does not allow this action, or the account is suspended. |
| `404` | The resource does not exist or you cannot access it. |
| `409` | The `X-Idempotency` key was already used for a different action or a different resource. Send a new key. |

Errors use the [standard error format](/api#errors).
