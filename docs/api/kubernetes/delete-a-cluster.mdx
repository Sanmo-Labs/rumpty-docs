<Endpoint method={"DELETE"} path={"/v1/kubernetes/clusters/{uid}"} />

Queues deletion of the cluster and all of its nodes. The cluster and its nodes move to
`deleting` straight away, and the cluster disappears from listings once the operation
finishes.

This is asynchronous. It returns `202 Accepted` with an `operation_id`. See
[Get an operation](/api/operations/get-an-operation). A cluster can be deleted in any
status except `deleting` and `deleted`, including while it is `stopped`.

`X-Idempotency` is optional. A retry with the same key for the same cluster returns the
original operation with `200 OK` and `is_replay: true`, even after the cluster is gone.
Without a key, a repeated delete returns `409` because the cluster is already deleting.

The response's `cluster` includes `kubeconfig` when one exists.

## Authentication

Send your [API key](/api#authentication) as `Authorization: Bearer <token>`. The request is scoped to the workspace in `X-Workspace-Slug`.

</Param>

## Headers

<Param name={"X-Workspace-Slug"} type={"string"} required>

Slug of the workspace the request acts on. You can also pass it as the `workspace_slug` query parameter.

</Param>

<Param name={"X-Idempotency"} type={"string"}>

Optional unique key for this request, such as a UUID. Leading and trailing spaces are
trimmed. If you send a key you already used for the same action on the same cluster, the
original operation is returned with `200 OK`, `is_replay: true` and the
`X-Idempotency-Replay` header, and nothing new is queued. The replay is checked before the
cluster's current state. Reusing a key for a different action or resource returns `409`
with `action: idempotency_key_reused`. Keys are scoped to you and the workspace and shared
by every resource type.

</Param>

<Param name={"status"} type={"string"} required enumValues={["provisioning","running","stopped","failed","deleting","deleted"]}>

Lifecycle state. `failed` means provisioning or a later action failed. See
`last_failure`. `deleted` is only seen on [Get a cluster](/api/kubernetes/get-a-cluster)
and in idempotent replays.

`stopped` means the platform powered off every node because the account was suspended
for non-payment. A `running` cluster switches to `stopped` (and its nodes to `stopped`,
which ends node billing) as soon as the stop is queued, and stays stopped while the
account is suspended. Within about a minute of the account becoming active again it is
restarted: it goes through `provisioning` back to `running`, or to `failed` if the
restart fails. If the stop itself fails, the cluster goes back to `running` and the stop
is retried. A stopped cluster can still be deleted.
