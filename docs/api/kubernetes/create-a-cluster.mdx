<Endpoint method={"POST"} path={"/v1/kubernetes/clusters"} />

Queues a new Kubernetes cluster and returns `202 Accepted` with the `operation_id` of the
create operation. The cluster and its nodes start in `provisioning`. Poll
[Get an operation](/api/operations/get-an-operation) or
[Get a cluster](/api/kubernetes/get-a-cluster) until the cluster is `running`.

Every field except `name` is optional:

| Field | Default |
| --- | --- |
| `version` | `v1.36.2+k3s1` |
| `image_slug` | `ubuntu-2404-lts` |
| `control_plane_plan_slug` | `scale` |
| `worker_plan_slug` | `launch` |
| `worker_count` | `1` |

Things to know:

- The cluster runs in the default zone, `olas-closet`.
- Cluster names must be unique in the workspace. Uniqueness is checked on the slug of the
  name, so `Production` and `production` clash.
- Node names are derived from the cluster name: `<name>-cp-1` for the control plane and
  `<name>-worker-1`, `<name>-worker-2` and so on for workers.
- The API `endpoint` has the form
  `https://<slug>-<id>.k8s.rumptycloud.com:16443`, where `<id>` is a short fragment of the
  cluster's `uid`.
- Compute plans must be available. An unavailable plan returns `400`
  (`this compute plan is not available`).
- Past-due and suspended accounts get `402`.
- `X-Idempotency` is optional. A retry with a key you already used for a cluster create
  returns the original operation with `200 OK`, `is_replay: true` and the
  `X-Idempotency-Replay` header, and nothing new is queued. The replay is checked first
  (before billing, validation and the name check), so a retry after the cluster was created
  does not fail with `409` for the name. The same key with a different `name` returns
  `409` with `action: idempotency_key_reused`. Without a key, a retry of a create that
  already succeeded returns `409` because the name is taken.

## Authentication

Send your [API key](/api#authentication) as `Authorization: Bearer <token>`. The request is scoped to the workspace in `X-Workspace-Slug`.

<Param name={"X-Idempotency"} type={"string"}>

Optional unique key for this request, such as a UUID. Leading and trailing spaces are

Lifecycle state. `failed` means provisioning or a later action failed. See
`last_failure`. `deleted` is only seen on [Get a cluster](/api/kubernetes/get-a-cluster)
and in idempotent replays.

`stopped` means the platform powered off every node because the account was suspended
for non-payment. A `running` cluster switches to `stopped` (and its nodes to `stopped`,
which ends node billing) as soon as the stop is queued, and stays stopped while the
account is suspended. Within about a minute of the account becoming active again it is
restarted: it goes through `provisioning` back to `running`, or to `failed` if the
restart fails. If the stop itself fails, the cluster goes back to `running` and the stop
is retried. A stopped cluster can still be deleted.

## Errors

| Status | Meaning |
|---|---|
| `400` | Validation failed. Possible messages: `invalid request` (malformed JSON or missing `name`), `name is required` (blank name), `worker_count cannot exceed 3`, `invalid compute plan`, `this compute plan is not available`, `invalid image`, or `invalid ssh key`. |
| `401` | The API key is missing, invalid, expired or revoked. |
| `402` | The account is past due, so new paid resources cannot be created. |
| `403` | You cannot access the workspace, your role does not allow this action, or the account is suspended. |
| `409` | A cluster with the same name slug already exists in the workspace (`cluster name already exists`), or the `X-Idempotency` key was already used for a different operation (`action: idempotency_key_reused`). |

Errors use the [standard error format](/api#errors).
