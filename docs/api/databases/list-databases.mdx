<Endpoint method={"GET"} path={"/v1/databases"} />

Returns the workspace's databases, newest first. Deleted databases are not included, but
databases that are still `deleting` or that `failed` are.

Without query parameters, every database is returned in `data`. Send `page` or
`page_size` to paginate. A top-level `pagination` object is then added next to `data`,
and `q` filters the results. `q` is ignored unless `page` or `page_size` is present.

List responses never include the password. Use
[Get database credentials](/api/databases/get-database-credentials) for that.

## Authentication

Send your [API key](/api#authentication) as `Authorization: Bearer <token>`. The request is scoped to the workspace in `X-Workspace-Slug`.

## Query parameters

<Param name={"page"} type={"integer"} constraints={"min 1"}>

Page number, starting at 1. Values below 1 (or non-numbers) are treated as `1`. Sending this enables pagination.

</Param>

<Param name={"page_size"} type={"integer"} defaultValue={"10"} constraints={"min 1 · max 100"}>

Items per page. Defaults to `10`. Values above `100` are capped at `100`. Sending this enables pagination.

</Param>

<Param name={"q"} type={"string"}>

Case-insensitive substring search across the database's name, slug, engine, version, host, status and display status. Only applied when paginating.

</Param>

## Headers

<Param name={"X-Workspace-Slug"} type={"string"} required>

Slug of the workspace the request acts on. You can also pass it as the `workspace_slug` query parameter.

</Param>

<Param name={"status"} type={"string"} required enumValues={["provisioning","ready","stopped","deleting","deleted","failed"]}>

Lifecycle state. `provisioning` while being created, resized, restored or restarted,
`ready` when usable, `deleting` while being deleted and `failed` when the last create,
resize, restore, restart or delete failed. `deleted` only appears in an idempotent replay
of a delete.

`stopped` means the platform stopped the database because the account was suspended
for non-payment. A `ready` database switches to `stopped` as soon as the stop is queued
(compute billing stops), and stays stopped while the account is suspended. Within about
a minute of the account becoming active again it is restarted: it goes through
`provisioning` back to `ready` (or `failed` if the restart fails). While `stopped`,
actions that need a `ready` database (resize, password rotation, snapshots, the data
browser) return `409`. If the stop itself fails, the database stays `ready` and the stop
is retried.

</Param>
