<Endpoint method={"DELETE"} path={"/v1/databases/{uid}"} />

Queues deletion of the database and returns `202 Accepted`. The database moves to
`deleting` straight away and is removed from listings once the operation succeeds. If the
delete fails, the database moves to `failed`. Follow the operation with
[Get an operation](/api/operations/get-an-operation).

All data is destroyed. The database's snapshots are kept: they are detached from the
database and can still be listed with [List database snapshots](/api/databases/list-database-snapshots),
used to create a new database, or deleted.

The database can be deleted in any status except already deleted. Without
`X-Idempotency`, each call queues a new delete operation until the database is gone. With
a key, a retry returns the original operation with `200 OK` and `is_replay: true`, even
after the database has been deleted (`database.status` is then `deleted`).

## Authentication

Send your [API key](/api#authentication) as `Authorization: Bearer <token>`. The request is scoped to the workspace in `X-Workspace-Slug`.

<Param name={"X-Idempotency"} type={"string"}>

Optional unique key for this request, such as a UUID. Leading and trailing spaces are
trimmed. If you send a key you already used for the same action on the same resource, the
original operation is returned with `200 OK`, `is_replay: true` and the
`X-Idempotency-Replay` header, and nothing new is queued. The replay is checked before the
resource's current state, so a retry after the first request finished still gets the
original result. Reusing a key for a different action or resource returns `409` with
`action: idempotency_key_reused`. Keys are scoped to you and the workspace and shared by
every resource type. Without a key, every request queues a new operation.

</Param>

<Param name={"status"} type={"string"} required enumValues={["provisioning","ready","stopped","deleting","deleted","failed"]}>

Lifecycle state. `provisioning` while being created, resized, restored or restarted,
`ready` when usable, `deleting` while being deleted and `failed` when the last create,
resize, restore, restart or delete failed. `deleted` only appears in an idempotent replay
of a delete.

`stopped` means the platform stopped the database because the account was suspended
for non-payment. A `ready` database switches to `stopped` as soon as the stop is queued
(compute billing stops), and stays stopped while the account is suspended. Within about
a minute of the account becoming active again it is restarted: it goes through
`provisioning` back to `ready` (or `failed` if the restart fails). While `stopped`,
actions that need a `ready` database (resize, password rotation, snapshots, the data
browser) return `409`. If the stop itself fails, the database stays `ready` and the stop
is retried.
