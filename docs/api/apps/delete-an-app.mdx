<Endpoint method={"DELETE"} path={"/v1/apps/{uid}"} />

Deletes the app and all of its component deployments, **including their persistent
volumes and data**. The app and its components are marked deleted straight away (billing
stops and custom domains are released), and each component's runtime is torn down by its
own `delete_deployment` operation, web component first.

The response is `202 Accepted` with `status: deleted` and no `operation_id`. The
component operations are not returned; you can find them with
[List operations](/api/operations/list-operations). Because
the components are already deleted, they appear in the response with only `role` and
`deployment_uid`.

Concurrent deletes of the same app are serialized: while one is in progress, another
request returns `409` (`app deletion is already in progress`), unless it carries the same
`X-Idempotency` key, in which case it gets the first request's result.

Send `X-Idempotency` to make retries safe. The key is recorded when the delete starts,
so repeating the request with the same key returns `200 OK` with `is_replay: true`,
`is_completed: true` and `status: deleted` instead of `404`. On a replay the app is gone,
so `app` only carries `uid`, `name` and `status`. Reusing the key for a different action
or a different app returns `409` with `action: idempotency_key_reused`.

## Authentication

Send your [API key](/api#authentication) as `Authorization: Bearer <token>`. The request is scoped to the workspace in `X-Workspace-Slug`.
