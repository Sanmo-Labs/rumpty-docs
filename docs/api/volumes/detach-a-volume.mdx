<Endpoint method={"POST"} path={"/v1/volumes/{uid}/detach"} />

Queues detaching an `in-use` volume from its VM. The volume moves to `detaching` straight
away and back to `available` when the operation succeeds. Its data is kept. If detaching
fails, the volume stays `in-use` and `last_failure` explains why.

Unmount the filesystem inside the VM first to avoid losing unwritten data.

This is asynchronous. It returns `202 Accepted` with an `operation_id`. See
[Get an operation](/api/operations/get-an-operation). The `X-Idempotency` header is
optional. A retry with the same key for the same volume returns the original operation with
`200 OK`, before the volume's state is checked.

## Authentication

Send your [API key](/api#authentication) as `Authorization: Bearer <token>`. The request is scoped to the workspace in `X-Workspace-Slug`.

## Path parameters

<Param name={"uid"} type={"string"} required>

The volume's `uid`.

</Param>

## Headers

<Param name={"X-Workspace-Slug"} type={"string"} required>

Slug of the workspace the request acts on. You can also pass it as the `workspace_slug` query parameter.

</Param>

<Param name={"X-Idempotency"} type={"string"}>

Optional unique key for this request, such as a UUID. Leading and trailing spaces are
trimmed. If the key was already used for the same action (and the same volume, or for a
create the same name), the original operation is returned with `200 OK`,
`is_replay: true` and the `X-Idempotency-Replay` header, and nothing new is queued. The
replay is checked before the volume's current state, so a retry after the first request
finished still gets the original result. If the key was used for any other operation in
the workspace, including VM, database or snapshot operations, the request is rejected with
`409` and `action: idempotency_key_reused`.

</Param>
